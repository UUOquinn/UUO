    产品概览

    1. 主要实现什么

    联盟诊断工作台把日常要在多个内网系统里完成的事，收到一个页面里：

    • 工作台：漏斗诊断、查询记录（数据集管理灰显，预留）
    • 能力模块：策略查询、策略审核、策略延期、产品手册（CPM 排查灰显，预留）

    目标用户是联盟运营 / 策略同学：少切系统、少抄 Cookie、少在 Orient / KwaiBI 页面上重复点选。

    2. 主要用什么技术实现

    • 前端：原生 HTML / CSS / JS（无 React/Vue）：index.html、app.js、strategy-*.js、home.js
    • 生产后端（写死）：Python server/app.py，由本仓库 guardian.sh run 守护，默认 :3000 — 见 启动方式
    • 轻量 Node 后端：server/index.js（仅 KwaiBI 数据集代理，不含策略 / Orient）
    • 外部系统：KwaiBI（查数）、Orient / operation-tool（定投策略与审核）

    3. 遇到什么问题，怎么解决

    • 多系统切换成本高 → 统一侧栏工作台 + 服务端代理，浏览器只打本机 API
    • 同事免登录要求 → 服务端共享 Cookie / Playwright 持久化 session，个人覆盖可选
    • 能力尚未就绪 → 导航灰显「即将上线」，避免点进去空壳

    整体架构

    1. 主要实现什么

    浏览器请求本地工作台；工作台再代理到 KwaiBI / Orient，并提供离线策略表检索。

    2. 主要用什么技术实现

    • 漏斗查数：POST /api/dataset/query → KwaiBI /api/v1/dataset/data/query
    • 策略查询：Operation 实时 orientControl/query，POST /api/strategy/query
    • 策略审核 / 延期：代理 Orient：orientControl/*、approve/query、approve/changeStatus
    • 登录保活：优先 Playwright 共享浏览器 session → Chrome CDP → urllib + Cookie 三级降级

    生产请用 Documents 仓库 + guardian.sh run（见 启动方式）。仅跑 npm start（Node）时，策略查询 / 审核 / 延期不可用。

    3. 遇到什么问题，怎么解决

    • 内网 KSAP / SSO 拦截裸 Cookie 请求 → 优先用 Playwright 真浏览器会话发请求，而不是简单拼 Header
    • CORS / 自定义 Cookie 头 → 后端显式允许 X-Kwabi-Cookie，并做 OPTIONS 预检
    • 测试与生产互踩登录态 → :3001 staging 使用独立 orient_session_staging

    漏斗诊断

    1. 主要实现什么

    把自然语言业务问题转成可执行的诊断口径，并尽量拉真实数据做主漏斗对比与下钻建议。

    • 输入：问题描述；时间口径（自动 / 今天 / 历史 / 近 N 天）；异常指标；uid / app_id / pos_id / ad_style
    • 输出：目标指标、数据集选择、对比口径、结论与下一步、过滤条件；有数据时再出对比表与漏斗条
    • 典型用法：今天某广告位有效请求率下降

    2. 主要用什么技术实现

    • 前端规则引擎：关键词识别指标（METRIC_RULES）、时间口径、下钻方向（app.js）
    • 数据集：离线主效果 85587、实时主效果 129496、过滤原因 207512、召粗精漏斗 103846
    • 今天走实时集，历史走离线集；有效请求率下钻 207512，有效填充率下钻 103846
    • 服务端转发 KwaiBI；个人 Cookie 经 X-Kwabi-Cookie 覆盖

    3. 遇到什么问题，怎么解决

    • KwaiBI 不可达 / Cookie 过期 → 自动降级为「口径模式」：仍给出诊断方案，不阻断使用；顶栏状态徽标区分数据模式 / 口径模式
    • 207512 字段是 UUID → 前端映射表转成中文过滤比名称，方便阅读
    • 鉴权失败 → 识别登录页 HTML / 401 / 403，触发侧栏 Cookie 过期提示

    查询记录

    1. 主要实现什么

    服务端共享保留查询记录（最长 30 天），全员可见并尽量标注操作人；支持点击回填复用。

    2. 主要用什么技术实现

    • 后端：POST/GET /api/workbench/logs?type=query，JSONL 落盘 server/data/logs/
    • 前端：首页查询日志面板；操作人取自 postpone-operator / shield-plat-operator
    • 本地 localStorage 仅作短暂兜底，展示以服务端为准

    3. 遇到什么问题，怎么解决

    • 刷新/换浏览器丢记录 → 改为服务端持久化，最长 30 天自动裁剪
    • 跨人不可见 → 同一工作台进程共享一份 JSONL
    • 误清空影响全员 → 不提供全员清空，仅支持清除本机搜索筛选

    策略查询

    1. 主要实现什么

    按开发者 ID / 广告位 ID / 应用 ID（可组合，取交集）实时检索 Operation 定投策略；默认返回生效中与审核中策略，并按规则名称分桶做维度合集。

    • 示例：广告位ID 5118002323
    • 组合：开发者ID 12345 应用ID 926500003
    • 也可直接输入数字 ID（无明确字段时按应用 ID 处理）
    • 结果结构：匹配摘要 → 维度合集（屏蔽 / 明暗投 / 定投）→ 策略清单 → 单条明细

    2. 主要用什么技术实现

    • 前端：Agent 聊天壳 strategy-query.js（解析 ID、按规则分桶、渲染合集）
    • 后端入口：POST /api/strategy/query、GET /api/strategy/meta（server/app.py）
    • 实时查询包：server/modules/strategy_query/
      • live_query.py：orientControl/query 列表 + 必要时 orientControl/get 补全
      • orient_fields.py：Orient 对象 → 中文字段（规则名 / 投放范围 / 广告主维度，可复用）
    • 上游：正式环境 operation-tool.corp.kuaishou.com（cookie.json → Playwright / Chrome 降级）
    • 数据源：正式 Operation orientControl/query + 必要时 get 补全（不落本地全量表）

    规则名称与投放范围枚举（摘要）

    • 规则名称：API 无 ruleName，由 type 映射（如 5→标签屏蔽、7→新屏蔽并集、9→新联盟明暗投）
    • 投放范围：placements 映射（1→全生效、2→暗投、4→明投优选、5→明投）
    • 是否类：isAppDirect / shieldEquityCard / shieldSex → 是/否

    3. 遇到什么问题，怎么解决

    • 旧 Excel 长名单截断（约 32K） → 已弃用本地全量表，改实时 query/get
    • query 列表字段不全 / 无 ruleName → 缺维度时 get 补全 + orient_fields 枚举反查
    • 仅有 appId 就跳过 get → 改为「缺规则名或投放范围才 hydrate」，避免维度合集全空
    • Cookie 过期 / 未登录 → 返回 401，需服务端完成 Operation 登录
    • 数据新鲜度 → 每次用户查询实时打 Operation；meta 展示最近查询时间 dataAsOfText

    审核页的 approve 状态与本页「生效中 / 审核中」是两套体系；本页只展示策略生效维度，不做审核动作。

    策略审核

    1. 主要实现什么

    对接 Orient 审核平台（approve）与策略详情（*Control/get），支持按策略 ID / 提交人查询，并执行审核动作（可批量）。

    • 查询：13938 或 13938 14619 22856
    • 按提交人：审核人 wb_xxx（拉 status=1 待审列表；白名单用户可自动跑全流程）
    • 审核通过：通过 13938（approve 1→6）
    • 同意发布：发布 13938（approve 6→2；Orient 文案常为「发布成功」）
    • 完整审核：审核 13938 = 通过 → 发布 → 可推全则立即推全
    • 驳回 / 拒绝发布：驳回 13938、拒绝 13938
    • 立即推全：推全 13938（强制推全，不看按钮标志；业务状态不符会被 Orient 拒绝）
    • 封禁期通过 / 驳回：封禁通过 13938、封禁驳回 13938
    • 封禁审核：封禁审核 13938 = 封禁期通过(13) → 可推全则封禁期立即推全
    • 封禁期立即推全：封禁推全 13938

    铁律：「策略生效状态」（如「生效中」、greyStartTime）与「审核平台状态」（approve）是两套码表。生效中 ≠ 审核已发布 ≠ 已立即推全。

    封禁期没有「同意发布」步。封禁审核 = status 12→13 → 条件 quickPushAll type=2；普通审核才走 1→6→2 → 条件 type=0。

    普通 vs 封禁期编排

    • flow?mode=ban：12→13 → 条件 push type=2
    • flow?mode=publish_replay：只跑 6→2 + 条件推全（给卡单补跑用）
    • 推全门闩：displayQuickPushBtn / displayProhibitionPeriodQuickPushBtn（含 toolBar）；默认轮询约 4 次、间隔约 0.8s
    • 推全接口：POST /{orient|dark|flow}Control/quickPushAll?id=&type=；媒体/综合前缀通常跳过
    • 编排结果字段：auditOk / publishOk / pushStatus / stuckAt（发布失败且卡在 6 时 stuckAt=6）

    策略运行态（只读门闩，不替代审核流转）

    • 详情来自 orientControl|flowControl|darkControl|…/get
    • 前端常见生效态：1 待审核、2 待发布、3 审核中、4 生效中、5 已撤回、6 已结束、7 草稿
    • 数字码与 approve 重叠但语义不同，页面会分开展示

    3. 主要用什么技术实现

    • 前端：strategy-audit.js（指令 / 卡片 / 批量；列表路径传 creatorId + approveId）
    • 后端模块：server/modules/strategy_audit/（resolve / flows / push_full / auto_approve）
    • API：/api/strategy/audit/get、changeStatus、flow（normal|ban|publish_replay）、pushFull、queryByCreator（自动翻页）、users、batchPass、withdraw
    • 关键链路：策略 ID → approve/query（优先 creatorId / ruleId / 翻页）→ approve/changeStatus；已有 approveId 则跳过二次反查
    • 代理：Playwright → Chrome CDP → urllib（与查询/延期共享会话队列）

    4. 遇到什么问题，怎么解决

    • 未找到审核记录 → 多为全站列表首页 100 条漏单；已修：传 creatorId、复用列表 approveId、翻页/ruleId 直查
    • 操作[发布成功]无法应用于状态[审核成功] → 卡在 approve=6；自动审会补跑 status=6；手动可「同意发布」或 flow?mode=publish_replay
    • 推全跳过（按钮 false） ≠ 审核失败；当场轮询后仍不能推则结束，不再入推全补跑队列
    • 推全失败「无法应用于状态[…]」 → 策略侧不可推全（已生效/已发布成功等）；通道通但业务拒绝
    • 生效中但仍说没推全 → 先看审核单是否已到 status=2，再看 displayQuickPushBtn；不要只看策略详情
    • 不能审自己的单 / SSO 过期 → Orient 权限或 Cookie；走 Playwright 登录续期

    自动审核

    1. 主要实现什么

    白名单内提交人的待审策略由守护线程自动处理；加白即生效，删白即停止（热读 realtime-check.js）。

    • 默认间隔 300 秒（5 分钟）（环境变量 AUTO_APPROVE_INTERVAL）；启动后约 15 秒跑首轮（AUTO_APPROVE_START_DELAY）
    • status=1（normal）：审核通过(6) → 同意发布(2，失败最多重试 3 次) → 条件立即推全
    • status=6（publish_replay）：卡在「审核成功」的补跑 — 只同意发布 + 条件推全，不再打审核通过
    • status=12（ban）：封禁期通过(13) → 条件封禁期推全（不自动驳回）
    • 查询待审列表与手动 queryByCreator 共用翻页，避免 >100 条截断
    • 日志区分：反查失败 / 发布失败 / 推全跳过 / 推全失败；首页错误区据此解析

    • 代理：与手动审核相同三级降级；与查询/延期共享 Playwright 队列（queue_busy 时跳过并打日志）
    • 单测：python3 -m unittest modules.strategy_audit.tests.test_flows_unit

    3. 遇到什么问题，怎么解决

    • 改了代码不生效 → 需 bash guardian.sh restart；守护线程不热加载 Python 模块
    • 卡在审核成功(6) 永久不碰 → 旧逻辑只扫 1/12；现已每轮扫 6 补跑
    • 日志写「队列忙 / 提前结束」 → 查询或延期占用 Playwright；等下一轮，勿误判白名单失效
    • 正在执行时重复 trigger → 返回 ALREADY_RUNNING
    • 白名单格式错误 → 解析失败当空名单，不崩服务
    • 推全能力通但仍报审核失败 → 看日志是「发布失败」还是「推全跳过」；前者卡在 6，后者审核已成功

    策略延期

    1. 主要实现什么

    批量把定投策略结束时间顺延 1 个自然月，并自动提审——对齐 Orient 手动链路：搜 ID → 编辑 → 点「一月」→「修改并自动提审」。

    • 支持单个 / 多个策略 ID，或粘贴到期提醒文本自动抽 ID
    • 提审后可用「策略审核」完成后续审批，或到审核页人工确认
    • 托管表（方案 A）：右上角「托管表」维护自动延期名单；编辑需操作人账号白名单；后台定时扫到期策略自动延期（仅定向）— 详见 自动延期托管

    2. 主要用什么技术实现

    • 前端：strategy-renewal.js（get → 改 endTime → submit）；strategy-postpone.js（托管表 UI）
    • 后端：POST /api/strategy/renew/get、/submit；托管 /api/strategy/postpone/*
    • 包：server/modules/strategy_postpone/automation_postpone/
    • 上游：Orient orientControl/get + orientControl/mergeEditV2
    • 提交体：仅保留抓包验证过的白名单字段；并补齐隐藏字段 adCluster.industryVersion = "6.6"

    3. 遇到什么问题，怎么解决

    • 业务码 412（不是普通 HTTP 挂了） → 多因多传字段或缺少行业版本；用字段白名单 + 强制 industryVersion 规避
    • 响应结构多层嵌套 → 逐层抽取含 adCluster / mediaCluster 的策略载荷
    • GET 可多类型、POST 延期当前写死 orientControl → 非定向类策略延期需谨慎，优先确认类型后再批量跑
    • 登录与 KSAP → 与审核相同，走 Playwright / CDP / Cookie 三级代理

    自动延期托管

    1. 主要实现什么

    策略延期页右上角「托管表」维护一份表驱动的自动延期名单：后台守护线程按节奏扫描，对名单中已开启的定向策略，在到期窗口内自动 endTime +N 月 并 mergeEditV2 提审。

    • 托管策略：策略 ID、负责人、顺延月数、备注、开关（enabled）
    • 编辑权限：管理员 / 编辑人白名单（postpone_editors.json）；admins 为空时为开放模式，任何人可写
    • 扫描规则：每天 09:00 定点扫描；剩余自然日 ≤7（含当天、已过期）才延期；仅定向 orientControl
    • 手动触发：托管表「扫描状态」页可立即扫一次，不等守护线程

    • server/modules/strategy_postpone/data/postpone_editors.json — 管理员与编辑人

    3. 遇到什么问题，怎么解决

    • 无权限编辑托管表 → 确认操作人已加入 postpone_editors.json 的 admins/editors；或 admins 为空时处于开放模式
    • 策略显示未到期不延 → 默认窗口为剩余 ≤7 自然日；可通过环境变量 POSTPONE_DUE_WITHIN_DAYS 调整
    • GET 失败 / 非定向 → 自动延期仅支持 orientControl/get 定向策略；扶持/暗投等会跳过或失败
    • mergeEditV2 业务 412 → 与手动延期相同，检查字段白名单与 industryVersion
    • 正在执行时重复触发 → run_once() 互斥锁返回 already_running
    • 提审后未生效 → 自动延期只完成提审；后续需「策略审核」或 Orient 审核页审批

    Cookie / 登录

    1. 主要实现什么

    让大多数用户打开就能查漏斗；个人有权限差异时，可本地覆盖 KwaiBI Cookie 并验证。

    • 默认：服务端共享配置（用户零配置）
    • 可选：侧栏粘贴个人 Cookie → 保存 →「验证」（对数据集拉一行试探）
    • 留空保存 = 清个人覆盖，回到服务端共享

    2. 主要用什么技术实现

    • 服务端文件：server/cookie.json 的 kwabi 字段
    • 个人覆盖：浏览器 localStorage → 请求头 X-Kwabi-Cookie
    • 状态接口：GET /api/cookie/status（区分 playwright / chrome / server 等来源）
    • Orient：主要依赖 Playwright 持久化 session，不完全依赖该 KwaiBI Cookie

    3. 遇到什么问题，怎么解决

    • KwaiBI Cookie 1–3 天过期 → 维护者更新 cookie.json；用户侧仅看到统一过期提示
    • CDP 里 JSESSIONID 与真实请求不一致 → 拦截真实 XHR Cookie，而不是只读 Cookie 存储
    • Orient 登录与 KwaiBI Cookie 易混淆 → 漏斗偏 Cookie；审核/延期看服务端 Playwright session

    常见认知澄清

    1. 生产环境请用 Python 后端（Documents + guardian.sh run）；Node 轻量服务不含策略与 Orient 能力。
    2. 漏斗「有 Cookie」≠ Orient「已登录」；两套认证通道。
    3. 延期 412 多为业务字段 / 行业版本问题，不要当成服务挂了。
    4. 策略查询每次用户查询实时打 Orient（orientControl/query + 必要时 get），不以 Excel 导入表为准。
    5. 审核时「生效状态」与「审核平台状态」是两套体系；生效中 / 有灰度时间 ≠ 已同意发布 ≠ 已立即推全。
    6. Orient 审核单 status=6 文案是「审核成功」，status=2 是「发布成功」；同意发布目标码是 2。
    7. 自动审每轮扫 status=1、补跑 status=6、封禁 status=12；改 Python 后需重启服务才生效。
    8. 「推全跳过」不是审核失败，也不再跨轮挂内存补跑；「发布失败 / 卡在审核成功」才会入发布卡单队列。
    9. 延期 GET 可多类型探测，提交仍写死 orientControl/mergeEditV2；勿与审核报错混为一谈。
